## Часть 1. Техническая сводка

### 1. Sensor fault propagation — закрыт главный HIGH-пробел
Был разрыв: драйверы `mf_sensor_scd41`/`mf_sensor_mlx90614` выставляли локальный `s_fault_disconnected`, climate-arbiter уходил в safe-timer, но **FSM никогда не получала `evFaultNonFatal(SENSOR)`** — DEGRADED_RUN был достижим только через SD-фейл. Recovery-streak считался в драйверах, но `mf_fsm_recovery_validated()` нигде не вызывался.

Добавлено:
- Новый модуль `firmware/mushfarm/mf_fault_supervisor.{h,cpp}` — каждый тик после `task_sensors()` делает edge-detect на `mf_*_fault_disconnected()` и публикует `mf_fsm_fault_nonfatal(MF_NONFATAL_SCD41/MLX90614/WATER)` на восходящем фронте, а на нисходящем — снимает соответствующий warn-флаг и (если все sensor-флаги чисты, и FSM в `DEGRADED_RUN`) публикует `mf_fsm_recovery_validated()`.
- Расширены enum'ы в `mf_fsm.h`: `mf_fsm_nonfatal_t` (SCD41, MLX90614, WATER), `mf_fsm_warn_t` (`MF_WARN_SCD41_FAIL`, `MF_WARN_MLX_FAIL`, `MF_WARN_WATER_FAIL`, `MF_WARN_CAMERA_FAIL`).
- `act_persist_warn_sd` → `act_persist_warn` (`mf_fsm.cpp`): теперь маршрутизирует по `ctx->nonfatal_code` в нужный бит warn-flags. SD-путь не сломан, новые источники просто переиспользуют те же rows в `k_transitions[]`.
- `mf_fsm_g_recovery_stable()`: блокирует recovery, пока выставлен любой sensor warn-флаг. SD-warn рекавери НЕ блокирует (был тихий side effect в старой реализации).
- Публичные `mf_fsm_set_warn(mask)` / `mf_fsm_clear_warn(mask)` для драйверов и супервизора с диагностическим логом.
- Test-хуки `mf_fault_supervisor_inject_fault/recovery()` для скетча тестов и будущего service-mode fault injection.

Этим закрыт DoD S2 («отключение датчика дает ожидаемый fault») по-настоящему и DoD S4 в части DEGRADED_RUN.

### 2. Water-policy — реализована полностью по fault-model.md §"Water Sensor"
Раньше арбитер делал голое `if (!mf_water_present()) hum = 0;` — никакого reserve timer, никакого pulse-safe, никакой RH-trend escalation. fault-model.md описывал детальную политику, которая не была реализована.

Новый модуль `mf_water_policy.{h,cpp}` с пятью состояниями:

```
NORMAL ──(LOW)──▶ RESERVE ──(reserve timer)──▶ PULSE_ON ⇄ PULSE_OFF
                                                   │
                                                   └─(3 flat-RH windows)──▶ LOCKED
   ◀──(water back)──────────────────────────────────                          (sticky)
```

- Reserve timer: `MF_WATER_RESERVE_TIMER_S = 60` (в `mf_config.h`).
- Pulse-safe: `MF_WATER_PULSE_ON_S = 15`, `MF_WATER_PULSE_OFF_S = 180` — точно по fault-model.md.
- Flat-RH trend: если за `MF_WATER_PULSE_FLAT_LIMIT = 3` ON-окна RH не выросла хотя бы на `MF_WATER_PULSE_RH_RISE_DELTA = 1.0%` — переход в LOCKED + публикация `MF_NONFATAL_WATER` (через супервизор).
- `mf_climate_arbiter` теперь вызывает `mf_water_policy_apply(hum, rh_now, dt)` вместо старого one-liner'а.
- `mf_climate_arbiter_reset()` дополнительно ресетит политику (вызывается при старте/смене стадии).

### 3. NTP/TZ + честный resume без wall-clock — починен тихий баг
Был баг: `mf_session_save` писала `stage_started_unix_s = mf_clock_unix_seconds()` (которая до синхронизации возвращала 0). На resume `elapsed = now_unix - 0 = 0`. То есть формально resume «работал», но **stage timer обнулялся** молча. Длинная стадия после ребута начиналась заново.

Сделано:
- `mf_clock.h`: новые API `mf_clock_time_synced()`, `mf_clock_monotonic_seconds()`, `mf_clock_init_ntp(tz, ntp1, ntp2)`.
- `mf_clock.cpp`: на boot только `setenv("TZ")` + `tzset()`; SNTP через `mf_clock_start_sntp()` после подключения STA (`MF_CLOCK_SNTP_ENABLED`). Threshold для synced — 2000-01-01.
- `mf_config.h`: `MF_CLOCK_TZ_POSIX "MSK-3"`, NTP-серверы, константы SoftAP `MushFarm_Setup` @ `192.168.4.1`.
- S6 модули: `mf_net_config`, `mf_wifi`, `mf_http_api`, `mf_actuator_test` — см. [s6-acceptance.md](architecture/s6-acceptance.md).
- `mf_nvs_session.cpp`: если `unix_seconds <= 0`, в лог пишется явное предупреждение про "no wall clock; resume will restart stage from 0" — никакого тихого вранья.
- `mf_fsm_resume_restore_from_nvs()`: явно проверяет `mf_clock_time_synced()` и `stage_started_unix_s > 0`. Если хотя бы одно условие не выполнено — логирует warn и стартует стадию с `elapsed = 0` (безопасно: дополнительные минуты в стадии не вредны, а укоротить стадию ложным числом — опасно).

### 4. Camera warn-flag — подключен
`mf_camera.cpp` теперь:
- При `MF_CAMERA_ENABLE=0` (по умолчанию): `status=disabled`, никаких warn — это намеренное отключение, не сбой.
- При `MF_CAMERA_ENABLE=1` без реального драйвера: `mf_fsm_set_warn(MF_WARN_CAMERA_FAIL)`. FSM-перехода НЕТ (так и записано в state-machine.md §"Camera Behavior per State"); status в трейсе показывает `stub_unimplemented`.

Это закрывает sticky-флаг `WARN_CAMERA_FAIL` из state-machine.md, который раньше был только в документации.

### 5. Service hook: симулятор воды в драйвере
Добавлен `mf_water_set_simulated_present(int level)` в `mf_sensor_water.{h,cpp}`. Семантика: `-1` — выкл, `0` — force LOW, `1` — force HIGH. Используется test-скетчем и пригодится для будущего service-mode actuator/sensor fault injection.

### 6. Trace расширен видимостью fault-pipeline
`task_trace` в `mushfarm.ino` теперь печатает `warn=0x..`, состояние water-policy (`wp=NORMAL/RESERVE/PULSE_ON/PULSE_OFF/LOCKED`) и `tsync=0/1` (NTP). За один взгляд видно, в какой стадии fault-цепочки находимся.

### 7. Тесты — отдельный sketch `firmware/mushfarm_tests/`
Скелет регрессионных тестов без хардвера:

| Suite | Что проверяется |
| --- | --- |
| Climate GV | GV1–GV9 из `docs/architecture/s5-acceptance.md` через `mf_mock_climate_set_scenario()`. Проверяет `arb_reason`, fan%, hum%, hard-limit флаги. |
| FaultSupervisor | Edge detection: inject SCD41 fault → `ACTIVE_RUN → DEGRADED_RUN` + `MF_WARN_SCD41_FAIL`. Inject recovery → `RECOVERY_VALIDATED → ACTIVE_RUN`. То же для water. |
| FSM core | pause/resume/emergency latch + ACK; pause во время latch — `ERR_LATCHED`; long-press из `IDLE_READY` → `SETUP_AP`. |
| WaterPolicy | NORMAL → RESERVE на первом LOW, восстановление воды во время reserve → NORMAL. (Полный 60+180 секундный цикл pulse в скетче не гоняется — это для bench-soak.) |

Архитектура: per-file shim (`src_*.cpp` — однострочники `#include "../mushfarm/mf_xxx.cpp"`), чтобы file-local `static`'и из mushfarm не конфликтовали при линковке. README в папке тестов поясняет.

Прогон: `firmware/mushfarm_tests/mushfarm_tests.ino` в Arduino IDE, Serial Monitor 115200, печатает `===== Result: N PASS, M FAIL =====`.

## Часть 2. Простая версия — на человеческом языке

1. **Датчики научились "стучаться" в мозги системы, а не молчать.** Раньше: датчик отвалился — драйвер про себя знал, что плохо, но система этого не видела и крутилась как ни в чём не бывало. Теперь: датчик отвалился — система это видит, переходит в "осторожный режим" (degraded), включает индикатор. Датчик ожил, 10 чтений подряд адекватные — система автоматически возвращается в полный рабочий режим.

2. **Бак с водой получил "несколько шансов".** Раньше: один раз сенсор показал "нет воды" — увлажнитель сразу выключился. Теперь по схеме из fault-model: подождать минуту (вдруг это волна качнула датчик), потом включать импульсами (15 сек включён / 3 минуты пауза, чтобы не сжечь увлажнитель на воздухе), и параллельно смотреть, растёт ли вообще влажность. Если 3 импульса подряд влажность не выросла — значит реально пусто, всё, увлажнитель окончательно блокируется и оператора уведомляют (degraded). Если в любой момент вода вернулась — мгновенно обратно в нормальный режим.

3. **Время. Большой тихий баг найден и исправлен.** Раньше: после внезапного отключения питания система пыталась вспомнить, на какой стадии выращивания она была. Стадию вспоминала правильно, но **сколько на этой стадии уже простояла — теряла** (читала 0, потому что часы без интернета не настроены). На длинных стадиях это могло удвоить время. Теперь: если часы не настроены — система честно об этом пишет в лог и стартует стадию с нуля (это безопасно: лишние минуты грибам не повредят, а сократить стадию ложными числами — опасно). Заодно подготовлено подключение к NTP-серверу — как только в S6 появится Wi-Fi, часы засинхронизируются автоматически без правки кода.

4. **Камера получила "галочку про проблему".** Раньше: камера упала — в логе одна строчка и всё. Теперь она ещё ставит специальный флажок (`WARN_CAMERA_FAIL`), который виден в общем трейсе и через будущий HTTP `/status`. По-прежнему ничего не блокирует — камера остаётся "красивой картинкой", не управлением.

5. **Тесты теперь живут отдельным скетчем.** Это не CI и не TDD-инструмент — это "включил Arduino IDE, прошил тестовый скетч, увидел в Serial Monitor 'N PASS, M FAIL'". Можно после любого изменения за минуту проверить, что не сломали ни один из 9 golden vectors (GV1–GV9), ни цепочку sensor-fault → degraded, ни базовые переходы FSM. По-настоящему ценно когда придёт железо и можно будет ещё запустить bench-soak отдельно.
